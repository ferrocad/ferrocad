# Spike: OCCT shape history

Status: spike report (2026-10-06). Companion to
[`geometry-and-topology.md`](geometry-and-topology.md) (the lineage/naming plan) and
[`mvp-path.md`](mvp-path.md) (the geometry-free MVP). This records the first,
deliberately small, experiment toward the geometry kernel.

**Goal.** Answer one question before any trait or crate is designed: does OCCT
expose enough *shape history* for a stable element map? The experiment is
[`../spikes/occt-history/`](../spikes/occt-history/): build two boxes, fuse, fillet,
and dump `Modified`/`Generated`/`Deleted` per input sub-shape.

---

## 1. Environment result (the sandbox cannot run the probe)

The authoring sandbox has:

- **no OCCT** (no headers, no libraries, anywhere on disk);
- **no network** (APT and crates.io unreachable);
- **no passwordless `sudo`** (interactive authentication required).

So the probe could not be compiled here. It is committed ready to run where OCCT
7.8+ exists (see the spike README for the two commands). This is a finding about our
**CI and build story**, not just the sandbox: any geometry milestone needs an OCCT
toolchain in CI, and that is a real cost to budget (see
[`distribution.md`](distribution.md)).

Because the empirical part is blocked, the rest of this report is the **offline
part of the spike**: reading what FreeCAD actually depends on. That turned out to be
more useful than a single box/fuse run, and it changes the plan.

---

## 2. Finding 1: FreeCAD does not use stock OCCT booleans

FreeCAD wraps every boolean in its own subclasses, added in 2024, precisely because
stock behaviour is not good enough for stable naming:

| File | What it adds over `BRepAlgoAPI_*` |
| --- | --- |
| `src/Mod/Part/App/FCBRepAlgoAPI_BooleanOperation.{h,cpp}` | Auto-fuzzy, non-destructive, recursive compound handling |
| `FCBRepAlgoAPI_Fuse/Cut/Common/Section.{h,cpp}` | Thin operation-specific subclasses |

The base wrapper (`FCBRepAlgoAPI_BooleanOperation`) does three things that matter:

- **Auto-fuzzy.** `FCBRepAlgoAPIHelper::setAutoFuzzy` sets the fuzzy value to
  `FuzzyHelper::getBooleanFuzzy() * sqrt(bounding-box extent) * Precision::Confusion()`,
  scaled to the model size. Fuzzy tolerance decides which faces are coincident, which
  decides what history reports as `Modified`.
- **Non-destructive.** `SetNonDestructive(Standard_True)` keeps the original
  topology available so the mapper can trace it.
- **Recursive compounds.** `RecursiveCutFusedTools` / `RecursiveCutCompound`
  decompose a compound `Cut` tool into a fuse-then-cut sequence, so a cut does not
  produce an unhelpful compound result.

**Consequence for our trait.** A `GeometryEngine::fuse` that naively wraps
`BRepAlgoAPI_Fuse` will produce *different* history than FreeCAD, hence a different
(and worse) element map. Either we port this behaviour, or we accept weaker naming.
This is a strong argument for doing the OCCT spike *before* freezing the trait, as
[`geometry-and-topology.md`](geometry-and-topology.md) §6–§7 already recommends.

## 3. Finding 2: the history surface (the exact calls to expose)

The element mapper consumes history from a small, well-defined set of OCCT APIs.
This is the minimal FFI surface the kernel side must provide:

| Purpose | OCCT API |
| --- | --- |
| Per-operation history (binary) | `BRepBuilderAPI_MakeShape::Modified/Generated/IsDeleted` |
| Richer history object | `BRepTools_History::Modified/Generated/IsRemoved`; `BRepAlgoAPI_BuilderAlgo::History()` |
| Fix-up history | `ShapeFix_Shape::Context()->History()` |
| Defeaturing | `BRepAlgoAPI_Defeaturing` |
| Sub-shape addressing | `TopExp::MapShapes`, `TopExp_Explorer`, `TopoDS_*`, `TopTools_IndexedMapOfShape` |
| Validity / bounds | `BRepCheck_Analyzer`, `Bnd_Box` + `BRepBndLib` |
| Tessellation (viewport, later) | `BRepMesh_IncrementalMesh`, `Poly_Triangulation` |

FreeCAD's `TopoShapeExpansion.cpp` forwards all of this into a `MapperHistory`
wrapper that folds operation history into mapped element names
(`Part::TopoShapeMapper.h`).

## 4. Finding 3: naming is *assigned*, never reported

OCCT reports *relationships* ("input face A was modified into output face X"). It
never gives an element a durable name. Every stable name in FreeCAD
(`Face6`, `;FUSED;...`) is generated by FreeCAD from that history and stored in a
`Data::ElementMap` attached to the shape (`src/App/ElementMap.h`).

This confirms the design rule in
[`geometry-and-topology.md`](geometry-and-topology.md) §5: the map is a side table
over the kernel's history, not a property of the kernel.

---

## 5. Finding 4: the element map is versioned and re-derived

Two facts decide our persistence format:

- `TopoShape::getElementMapVersion()` returns a **composite string**:
  `OpCodes::Version . <occt-hex> .` plus `ComplexGeoData::getElementMapVersion()`
  which is currently `"5"`. Notably, `_getElementMapVersion` **pins the OCCT version
  to `0x070200`** on purpose, so a kernel upgrade does not spuriously invalidate
  saved maps.
- `PropertyPartShape::Save` writes the shape **and** `ElementMap="<version>"`; on
  `Restore`, `checkElementMapVersion` decides whether the stored map is still valid.
  If not, the map is **re-derived** (the shape carries a `Hasher` that can redo it).

So the persistence answer is concrete: **persist the shape with a version-tagged
element map, and re-derive on version mismatch.** That is a decision we can freeze
now, in the format we control, before any geometry exists.

## 6. Finding 5: the B slices already touch geometry

The user hoped the spike would say something about the B slices. It does.

- **`App::Link` is not a geometry-free link.** It carries `LinkPlacement` (with a
  `Placement` alias), `Scale`/`ScaleVector`, a `LinkTransform` flag choosing which
  placement applies, and it can target a **list of sub-elements** by name
  (`getSubElements`, `mySubName`). Its placement composes with the linked object's
  (`getPlacementOf`). A `B3` that models only "object points at object" is a partial
  `Link`.
- **Containers compose placements recursively.**
  `GeoFeatureGroupExtension` exposes `placement()`, `transformPlacement`,
  `globalGroupPlacement`, and `recursiveGroupPlacement`. The container slice needs
  the placement algebra across nesting; we already have `Placement` in
  `ferrocad_core`, so this is reachable.
- **Sub-element references are the persistence hinge.** A `LinkSub`'s subnames
  (and a link's element list) are exactly the names the element map must keep stable.
  The moment links can address sub-elements, the persistence format and the lineage
  work are entangled.

Practical read: **B3/B5 can proceed mostly as planned**, but the object model should
carry the *fields* a `Link` needs (placement, scale, transform flag, sub-element
list) even while the shape output stays behind the geometry seam. Do not model a
`Link` as a bare pointer.

## 7. Recommended revisions to the plan

1. **Do not design the trait from stock OCCT.** Fold Finding 1 into §6 of
   [`geometry-and-topology.md`](geometry-and-topology.md): the engine must expose
   auto-fuzzy / non-destructive / recursive-compound behaviour, or naming degrades.
2. **Freeze the element-map persistence shape now.** Version tag + re-derive on
   mismatch (§5). This is format work we can do without a kernel.
3. **Add OCCT to the CI/packaging budget** (§1, [`distribution.md`](distribution.md)).
4. **Let B3/B5 carry Link's geometry-facing fields** (§6) without pulling in shapes.
5. **Run the committed probe** on a machine with OCCT 7.8+ and record the raw output
   here before finalizing the trait.

---

## 8. Open questions

- Which Rust binding, and whether it exposes `BRepTools_History` /
   `BRepAlgoAPI_BuilderAlgo::History`, not just the binary accessors. Unverifiable
   offline.
- Whether to port `FCBRepAlgoAPI_*` exactly, or only the parts that affect naming.
- BREP vs STEP as the on-disk shape encoding for our own format (FreeCAD uses BREP
  inside the zip container).
- Whether the element-map version we choose should mirror FreeCAD's string so a
   future `.FCStd` import can reuse maps, or diverge for a cleaner scheme.
