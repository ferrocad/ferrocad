## P4 — Constraints and sketches, with a bound solver

**Scope decision (2026-10-29): FerroCAD owns everything around the solver and does not
write one by default.** The constraint model, storage, selectors, diagnostics and UX are
ours; the numerical solve comes from an existing C++ solver (or, if that fails, a Rust
solver library). Writing a solver is the fallback, not the plan.

### 4.1 Solver options

| Option | Source at `33adf61` | Notes |
| --- | --- | --- |
| **PlanGCS** (2D) | vendored: `src/Mod/Sketcher/App/planegcs` (`GCS`, `Constraints`, `Geo`, `SubSystem`, `qp_eq`) | what Sketcher uses today; 2D only; its constraint set is exactly the sketch vocabulary |
| **OndselSolver** (3D) | submodule: `src/3rdParty/OndselSolver` (`FreeCAD/OndselSolver` @ `4be80ee`) | what Assembly uses; 3D joint/constraint solve; whether it expresses sketch constraints well is **unverified** |
| **A Rust solver** | — | only if both bindings fail; it would have to match PlanGCS's constraint vocabulary to keep upstream sketches loading |

Binding route: a sibling `cxx` bridge crate, the same pattern as `ferrocad_occt`
(`cxx` + `cxx-build` over `.hxx` shims). PlanGCS being free of OCCT dependencies is
**to verify before committing** to that route; if it pulls anything in, build it as a
standalone static library with its own `build.rs`.

### 4.2 The 2D question

PlanGCS is a 2D solver, so the "2D is a special case of 3D" posture has to survive the
binding: keep **one** constraint model where a sketch is a constraint set restricted to a
plane, and put every 2D assumption inside the PlanGCS adapter rather than in the document
schema. That way assembly constraints (OndselSolver) and sketch constraints share types,
diagnostics and selection references, even if the numerics come from different libraries.

### 4.3 Slices

1. **SK1 — the constraint model.** Typed constraints (coincident, point-on-object,
   distance, horizontal/vertical, parallel, perpendicular, angle, tangent, equal, radius,
   concentric, symmetry) holding *selector* references resolved through
   `ferrocad_lineage`, not indices. *Acceptance:* a constraint set round-trips through
   `.FCStd`, resolves after a recompute that reorders edges, and reports a dangling
   reference as an error.
2. **SK2 — the solver adapter.** One trait over the chosen solver, with DOF analysis,
   redundant/conflicting detection and deterministic reporting mapped back to constraint
   ids. *Acceptance:* a triangle with three dimensions converges from a perturbed start;
   an over-constrained sketch returns the redundant set; the result is identical across
   runs.
3. **SK3 — `Sketcher::SketchObject` becomes real.** Add `Constraints` and a solve result,
   keep geometry as it is, and add `python/Sketcher` (`addConstraint`, `delConstraint`,
   `setDatum`, `solve`, `getDatum`). *Acceptance:* an upstream-shaped script builds a
   constrained sketch and reads back its DOF count. This also unblocks P2's
   `make_sketch`.
4. [ ] **SK4 — draw on a workplane.** *Acceptance:* draw a closed path on a tilted face and
   get a wire that lies on that face; one undo removes it.
   **Its supporting work landed in the 2026-10-29 round** — the world plane as a real
   state, the `WP` selector, three-point pick, `Part::DatumPlane`, the offset stem,
   ephemeral face binding for a starting tool, the polyline's in-flight vertex editing,
   the one active-action HUD, and `Tool::finish` returning a *creating*
   `InteractionCommit` that the edition turns into an object
   ([`record/2026-10-29-workplane-visual-hierarchy-and-grid.md`](record/2026-10-29-workplane-visual-hierarchy-and-grid.md)).
   What is left is the acceptance path itself: click points on a **bound** plane, through
   the existing snap path, close the wire, commit, and remove it with one undo. The gaps
   named per slice in [`tasks/workplanes.md`](tasks/workplanes.md) §8 (numeric entry, the
   hover rim) belong here. Numeric entry is specified in
   [`tasks/polyline-vertex-editing-and-active-tool-hud.md`](tasks/polyline-vertex-editing-and-active-tool-hud.md) §6.
5. **SK5 — path to solid.** Extrude the committed wire through `Part::Extrusion` with the
   direction and length in the command's dialog, `Solid` on. *Acceptance:* closed path on
   a face → solid in one transaction; editing the path updates the extrusion.
6. **SK6 — constraints as refinement.** Select path geometry, add a dimension, watch the
   profile and its extrusion update; an unconstrained drag still works. *Acceptance:*
   dimension edit re-solves the sketch and the solids downstream follow.

### 4.4 Decisions to take before SK1

- **Bind PlanGCS first, or go straight to the 3D solver?** Binding the 2D one is the
  smaller step and matches upstream sketches; the 3D one is the long-term model.
- **One constraint crate or two?** Posture: one, with the plane as data.
- **Where does the solve run?** In the sketch's `execute()`, so the DAG orders it, with a
  distinct "solved" / "failed" / "over-constrained" state rather than an invalid shape.
- **What does a constraint reference after a boolean?** Decide before SK1 whether
  constraints may target generated faces (they should be allowed to fail loudly).
