## P4 — Constraints and sketches, with a bound solver

**Scope decision (2026-10-29): FerroCAD owns everything around the solver and does not
write one by default.** The constraint model, storage, selectors, diagnostics and UX are
ours; the numerical solve comes from an existing C++ solver (or, if that fails, a Rust
solver library). Writing a solver is the fallback, not the plan.

### 4.1 Solver options

| Option | Source at `33adf61` | Notes |
| --- | --- | --- |
| **PlanGCS** (2D) | vendored: `src/Mod/Sketcher/App/planegcs` (`GCS`, `Constraints`, `Geo`, `SubSystem`, `qp_eq`) | what Sketcher uses today; 2D only; its constraint set is exactly the sketch vocabulary |
| **OndselSolver** (3D) | submodule: `src/3rdParty/OndselSolver` (`FreeCAD/OndselSolver` @ `4be80ee`) | what Assembly uses; 3D joint/constraint solve; whether it expresses sketch constraints well is **unverified** |
| **A Rust solver** | — | only if both bindings fail; it would have to match PlanGCS's constraint vocabulary to keep upstream sketches loading |

Binding route: a sibling `cxx` bridge crate, the same pattern as `ferrocad_occt`
(`cxx` + `cxx-build` over `.hxx` shims). **Verified 2026-10-30** (see the fan-out record):
PlanGCS is **not templated** — `GCS` is a namespace and `System`/`SubSystem`/`Point`/`Line`/
`Constraint` are ordinary classes — so the `cxx` template limit does not apply. Its complete
external dependency set is `<Eigen/{QR,Sparse}>`, one Boost graph header, `SketcherGlobal.h`,
`Base/{Tools,Console}.h`, `FCConfig.h` and one FreeCAD-provided Boost shim; **no OCCT**.
Eleven files, ~13.3k lines, LGPL-2.1-or-later, no build file of its own — so vendoring it
unmodified plus four stub headers is mandatory (the upstream checkout is sparse and the
build is offline). OndselSolver is **not checked out** (`git submodule status` reports
`-4be80ee…`); initialise it before judging the 3D option.

### 4.2 The 2D question

PlanGCS is a 2D solver, so the "2D is a special case of 3D" posture has to survive the
binding: keep **one** constraint model where a sketch is a constraint set restricted to a
plane, and put every 2D assumption inside the PlanGCS adapter rather than in the document
schema. That way assembly constraints (OndselSolver) and sketch constraints share types,
diagnostics and selection references, even if the numerics come from different libraries.

### 4.3 Slices

1. **SK1 — the constraint model.** Typed constraints (coincident, point-on-object,
   distance, horizontal/vertical, parallel, perpendicular, angle, tangent, equal, radius,
   concentric, symmetry) holding *selector* references, not indices. **Prerequisite found
   by the 2026-10-30 fan-out:** `ferrocad_lineage` names *shape* sub-elements only, and a
   sketch stores a list of edges with no id, so there is nothing stable to reference yet.
   Add a document-scope geometry id (UUID + curve parameters) to the geometry entry first,
   then store constraints as `(object, geometry id, PointPos)` + kind + params and resolve
   them in `execute()` and on load. Upstream persists positional integers, so this is a
   FerroCAD extension that must migrate from them. *Acceptance:* a constraint set
   round-trips through `.FCStd`, resolves after a recompute that reorders edges, and
   reports a dangling reference as an error. The vocabulary is the upstream
   `ConstraintType` set (geometric, dimensional, and internal-alignment with an
   `Unknown(i32)` arm).
2. **SK2 — the solver adapter.** One trait over the chosen solver, with DOF analysis,
   redundant/conflicting detection and deterministic reporting mapped back to constraint
   ids. *Acceptance:* a triangle with three dimensions converges from a perturbed start;
   an over-constrained sketch returns the redundant set; the result is identical across
   runs.
3. **SK3 — `Sketcher::SketchObject` becomes real.** Add `Constraints` and a solve result,
   keep geometry as it is, and add `python/Sketcher` (`addConstraint`, `delConstraint`,
   `setDatum`, `solve`, `getDatum`). *Acceptance:* an upstream-shaped script builds a
   constrained sketch and reads back its DOF count. This also unblocks P2's
   `make_sketch`.
4. [ ] **SK4 — draw on a workplane.** *Acceptance:* draw a closed path on a tilted face and
   get a wire that lies on that face; one undo removes it.
   **State verified 2026-10-30:** the routing landed (a creating `InteractionCommit` reaches
   the host) and the snap path landed (clicks unproject onto the active plane, and a
   press on a planar face binds it). The **creation half does not exist**: the parametric
   edition registers only `workplane_points` and the two Part manipulators, and
   `_interaction` handles only `transform`/`push_pull`/`dress_up`. The only paths that build
   anything are the toy edition (`App::FeaturePython` + a float list, not a wire) and
   Draft's `make_wire` (not registered, and outside a transaction, so it is not undoable).
   Three slices, in order: **(a)** close the loop in `PolylineTool` (a click within the
   vertex radius of point 0, with ≥ 3 points, closes and finishes); **(b)** register the tool
   in the parametric edition and add a `create` provider that builds one `Part::Feature` via
   `Part.makePolygon` inside one named transaction — this is what makes undo work;
   **(c)** the acceptance test: four snapped clicks on a tilted plane, every vertex within
   f32 tolerance of the plane, one `doc.undo()` removes it.
   Two risks worth deciding first: there are now **two creation pipelines** (the Rust commit
   and Draft's `make_wire`) and only one may be the acceptance path; and a click that *hits
   geometry* returns the raw hit point rather than a plane projection, so a `WP` offset
   plane is silently violated — project tool points onto the active plane, or accept that
   "on the face" holds only while the plane equals the clicked face. The gaps named per
   slice in [`tasks/workplanes.md`](tasks/workplanes.md) §8 (numeric entry, the hover rim)
   belong here; numeric entry is specified in
   [`tasks/polyline-vertex-editing-and-active-tool-hud.md`](tasks/polyline-vertex-editing-and-active-tool-hud.md) §6.
5. **SK5 — path to solid.** Extrude the committed wire through `Part::Extrusion` with the
   direction and length in the command's dialog, `Solid` on. *Acceptance:* closed path on
   a face → solid in one transaction; editing the path updates the extrusion.
6. **SK6 — constraints as refinement.** Select path geometry, add a dimension, watch the
   profile and its extrusion update; an unconstrained drag still works. *Acceptance:*
   dimension edit re-solves the sketch and the solids downstream follow.

### 4.4 Decisions to take before SK1

- **Bind PlanGCS first, or go straight to the 3D solver?** **Settled for 2D** by the
  2026-10-30 fan-out: PlanGCS is standalone and dependency-light, OndselSolver is absent and
  unverified for sketches. What remains open is only whether Ondsel is ever needed for
  assembly.
- **One constraint crate or two?** **Settled by the tree's own pattern**: one
  kernel-free model crate (like `ferrocad_lineage`) and one solver-binding crate (like
  `ferrocad_occt`).
- **Where does the solve run?** In the sketch's `execute()`, so the DAG orders it. The open
  part is the *state channel*: today `mark_invalid` is the only failure signal, so
  "solved / failed / over-constrained" needs a new one before SK2 can report.
- **What does a constraint reference after a boolean?** The question is misframed: constraints
  reference sketch geometry, and a sketch stores edges with **no stable id** at all. The real
  prerequisite is SK1's geometry identity (see §4.3), and the open decision is whether an
  attached sketch re-maps when its support's lineage changes — there is no mapping to
  re-map today (`MapMode` is stored and never read).
