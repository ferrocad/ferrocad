# User documentation

FerroCAD has two kinds of user: **UI users**, who work in the application window,
and **API users**, who work through the Python console, a macro or a script. They
share the same document model; the API is the contract and the window is one client
of it. The gentle introduction is
[UI users and API users](explanation/ui-and-api.md).

## Two readers

- **UI users** — the window is the guide. The [UI controls](explanation/ui-controls.md)
  section maps its chrome, toolbar, action bar, wheel and loadout; the generated pages
  below are not click-throughs, and the [repository README](../../README.md) shows the
  window.
- **API users** — the pages below are your examples. They run the same `FreeCAD`
  calls as a console line, a macro or a script, with no window at all.

The task pages are generated by running an ordinary Python script against the real
`FreeCAD` facade: the code blocks are the code that executed and the tables are the
values it read back. The explanation pages are authored. The pages are grouped the way
Diátaxis groups them: a **tutorial** teaches by doing, a **how-to guide** answers one
task, the **reference** lists what exists, and an **explanation** page says why. Reference
is the generated [Python API reference](../python-api/index.md); the addon contract is
[`mods/`](../mods/README.md). A workflow that is not implemented has no script, so it has
no page — this index is the progress list, not a backlog.

## Explanation

Understanding-oriented: why it works this way.

- [How a click becomes a document edit](explanation/how-the-shell-talks-to-the-document.md) — This page explains the shape of the system from the outside in. It is the answer to a question the how-to guides skip: *why* does the code look the way it does?
- [The action bar](explanation/ui-action-bar.md) — The action bar is the strip that floats at the **bottom-centre** of the canvas. It carries the commands that create something or act on the whole document; the verbs that depend on what is under the pointer live in the wheel menu. That split is why the action bar does not change width when the selection changes.
- [UI users and API users: a gentle introduction](explanation/ui-and-api.md) — FerroCAD has two kinds of user — **UI users** and **API users** — and they are easy to confuse. Both work on the same document; the difference is the surface they use.
- [Window chrome](explanation/ui-chrome.md) — The chrome is everything around the canvas that belongs to the window rather than the document: the title bar and its application menu, the status line, and the separate Dev Tools window.
- [UI controls: the window at a glance](explanation/ui-controls.md) — FerroCAD's main window is deliberately spare: the 3-D viewport fills the canvas, and the controls that act on it float over the scene instead of reserving rows at the top and bottom. This section describes the controls you meet there, where each one lives, and what it changes. Each control page pairs a highlighted window snapshot with a close-up, in a **Desktop / Web** tab pair: the desktop tab shows the full application chrome and the manipulators, and the web tab shows the same shell in the browser.
- [Extrude (Push/Pull)](explanation/ui-extrude.md) — **Extrude** is the positive half of the **Push/Pull** hand in Slot 2. The same stem pockets when the distance is negative. Select a planar face, equip Push/Pull (`2`), and the face grows a stem along its outward normal.
- [Fillet](explanation/ui-fillet.md) — **Fillet** is Slot 3 of the loadout. Select an edge, equip Fillet (`3`), and the edge grows a radius scrubber. Dragging it sets the radius; the same handle chamfers when the edition offers the second distance.
- [Move](explanation/ui-move.md) — **Move** is Slot 1 of the tool loadout: it is the hand that translates a body with the shared transform triad. It is also the hand the wheel's `Move` verb equips.
- [Rotate](explanation/ui-rotate.md) — **Rotate** is the second handle set of Slot 1. The loadout keeps one hand, so the slot names what you will actually get: `1 Move` for the arrows, `1 Rotate` for the rings. Pressing `1` while Slot 1 is already active toggles between them; the wheel's `Rotate` verb also equips the Rotate hand, and the next pick arms the rings.
- [The tool loadout](explanation/ui-tool-loadout.md) — The tool loadout is the bar at the **bottom-left** of the canvas. FerroCAD's pointer carries **one hand at a time**; the loadout names the equipped hand, shows its key, and switches it.
- [The viewport toolbar](explanation/ui-toolbars.md) — The environment controls are a compact, translucent pill floating in the **top-left** of the canvas. It is not a pane header: the scene reaches the title bar, and the pill occludes only itself, so a press on the canvas beside it still orbits or selects.
- [The wheel menu](explanation/ui-wheel-menu.md) — The wheel menu is a radial marking menu that opens at the pointer. It exists so an object verb is one gesture away: you do not have to find a permanent toolbar row, and the action bar does not have to reflow every time the selection changes.

## Regenerating and capturing

```sh
python3 tools/userdocs.py                # refresh every page
python3 tools/userdocs.py --check        # non-zero exit if a page or image is stale
python3 tools/userdocs.py --capture      # re-render the images (needs a GPU adapter)
python3 tools/userdocs.py --write-manifest  # adopt existing PNGs without a GPU
python3 tools/build_book.py              # assemble the mdBook edition
```

The check is the part that matters: it is cheap, needs no GPU, and it is what
keeps the pages honest in review and in CI. The mdBook edition is assembled from
these pages, so it inherits the same guarantee.

## Screenshots and their limits

The screenshots are real viewport pixels, captured by
`python3 tools/userdocs.py --capture` from the render specs the workflows record
and stored under `docs/user/images/`. Capturing needs a GPU adapter; the pages and
the `--check` gate only read the committed PNGs, so CI stays cheap and GPU-free.
On a machine with no adapter the capture says so and leaves the images untouched.

`docs/user/images/manifest.json` pins each generated image to its render spec and
its PNG bytes. `--check` compares both, so a changed camera or shape fails review
even without a GPU. A page may also use a hand-supplied illustration (no render
spec); those are deliberately absent from the manifest. For a one-off viewport
image outside the page pipeline, use `tools/screenshot.py`; its `--mode chrome`
captures the app window (title bar, header controls, Dev Tools) and `--mode desktop`
captures the display. See
[`../developer/workbenches/screenshot-tool.md`](../developer/workbenches/screenshot-tool.md) for the three
scopes and when to use each.

What the pages are **not** is a claim of upstream parity. Only what runs here is
documented here; the gap is measured by
[`../developer/workbenches/conformance.md`](../developer/workbenches/conformance.md).
